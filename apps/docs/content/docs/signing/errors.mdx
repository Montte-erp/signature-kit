**What you'll do:** handle `SignatureKitError` in Effect's error channel, understand its stable fields, and deep-link to the exact code that failed.

<Callout type="info" title="Typed error channel">
  Failures are not `throw`: they live in Effect's error channel as a `SignatureKitError` with a literal `code`. The compiler forces you to handle them — or let them propagate, typed — instead of discovering them at runtime.
</Callout>

## The shape of the error

`SignatureKitError` is a class with a fixed `_tag` of `"SignatureKitError"`. Its fields:

- `code` — one of the literal `signature-kit.*` codes from the catalog below.
- `retryable` — a boolean decided **at the point of failure**, not fixed per code.
- `reason` — human diagnostic text when it is safe and useful.
- `operation`, `provider`, `schemaName`, `issueMessage`, `status`, `url` — structured origin metadata when the source has a real contract.

```ts title="handle-error.ts"
import { Effect } from "effect"

program.pipe(
  Effect.catchTag("SignatureKitError", (error) => {
    switch (error.code) {
      case "signature-kit.INVALID_INPUT":
      case "signature-kit.RESPONSE_SHAPE":
      case "signature-kit.UNSUPPORTED_OPERATION":
        return Effect.fail(error.message)
      default:
        return Effect.fail(error.message)
    }
  }),
)
```

The formats and signers are separate packages — install only what each path uses.

```package-install
@signature-kit/xml @signature-kit/pdf @signature-kit/http @signature-kit/clicksign
```

## Format catalogs

The format packages define their own error classes for local document failures. Use the `signature-kit` catalog for shared certificate/HTTP/schema failures and the format catalog for PDF/XML/CMS-specific operations.
